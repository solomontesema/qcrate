# Q-Crate R5 FreeRTOS and OpenAMP vertical slice

This milestone proves a complete heterogeneous-control path on the KV260:

```text
A53 Linux qcrate-control / qcrate-sequence
        |
        | /dev/rpmsgN (rpmsg_char)
        v
VirtIO RPMsg shared memory and IPI
        |
        v
R5-0 FreeRTOS qcrate-control service
        |
        | bounded APB operations and sequencer ownership
        v
Q-Crate SYS and SEQUENCE registers
```

It is deliberately a small vertical slice. It proves Linux `remoteproc`,
FreeRTOS, OpenAMP, VirtIO/RPMsg, shared-memory carveouts, IPI notification, a
versioned application protocol, R5 access to the fixed PL, and deterministic
sequencer ownership. Stream and DMA ownership remain on Linux.

## Architecture decisions

The alternatives considered were:

| Decision | Alternatives | Selected approach and reason |
|---|---|---|
| RPU mode | R5 lockstep; split R5-0/R5-1 | Split mode, using R5-0 now. It preserves R5-1 for later work and teaches explicit core ownership. |
| R5 operating environment | Standalone/bare-metal; FreeRTOS | FreeRTOS immediately, because task/ISR ownership and deterministic scheduling are project goals. |
| Linux/R5 transport | Ad hoc shared memory; custom mailbox protocol; OpenAMP | Linux remoteproc plus VirtIO RPMsg/OpenAMP, using the standard kernel and AMD software stacks. |
| Linux userspace interface | Custom kernel protocol driver; `rpmsg_char` | `rpmsg_char` for this bounded control service. A custom driver is justified later only if the protocol needs kernel ownership, concurrency, or a stable subsystem API. |
| R5 firmware launch | Put the ELF in `BOOT.BIN`; Linux runtime load | Linux `remoteproc` loads the ELF. This gives Linux explicit lifecycle ownership and is the normal OpenAMP development path. |
| Register access | Arbitrary remote MMIO commands; explicit operations | Explicit `PING`, `GET_INFO`, and `SCRATCH_TEST` commands. The R5 service is not an unrestricted APB proxy. |
| Sequence upload | Shared DDR buffer; multiple events per RPMsg packet; one event per packet | One event per fixed-size request. At the 128-event hardware limit this is bounded, simple to validate and retry, and keeps shared-memory ownership out of the control path. |

Register ownership is intentionally narrow:

- SYS identity registers are readable by Linux and R5.
- SYS scratch is diagnostic and is restored after the R5 test.
- STREAM registers and AXI DMA remain owned by the Linux `qcrate-dma` path.
- The entire SEQUENCE register page and event RAM are R5-owned. Linux uses the
  typed RPMsg commands and must not write that APB page directly.
- DMA descriptors and buffers remain Linux-owned.

- `kv260/vitis/`: reproducible Vitis 2024.2 scripts.

Generated and ignored:

The Vitis flow starts from AMD's `openamp_echo_test` template. It retains AMD's
generated ZynqMP machine layer, resource table, linker script, and OpenAMP

The tracked PetaLinux multiconfig also selects R5-0 FreeRTOS, so later SDK and
multiconfig work cannot silently fall back to the BSP's bare-metal default.

## IPI ownership and SDT input

Zynq UltraScale+ MPSoC Linux OpenAMP uses IPI 7 as the A53-side notification
endpoint and IPI 1 as the R5-0 endpoint. The default APU IPI remains available
to platform-management firmware. This is AMD's standard Linux OpenAMP
ownership model, not a PL data-path connection.

The accepted XSA describes the fixed IPI controllers but does not give IPI 7
the reciprocal RPU channels. Consequently, the Vitis 2024.2 OpenAMP SDT
generator cannot derive the mailbox buffer relationships from the XSA alone.
The tracked `kv260/vitis/qcrate_openamp_ipi.dtsi` supplies those relationships:

```text
A53/Linux IPI 7 request/response : 0xff990600 / 0xff990620
R5-0 IPI 1 request/response      : 0xff9900c0 / 0xff9900e0
A53/Linux IPI 7 request/response : 0xff990640 / 0xff990660 (R5-1 channel)
R5-1 IPI 2 request/response      : 0xff9902c0 / 0xff9902e0
```

`create_r5_firmware.py` passes this file through Vitis's supported
`user_dtsi`/`VITIS_SDT_INCLUDE_DTS` interface. These addresses match the
mailbox in `system-user.dtsi`, keeping Vitis-generated firmware and the Linux
driver on the same contract. AMD's stock 2024.2 ZynqMP OpenAMP YAML describes
both R5 channels and validates both before emitting the selected R5-0 domain,
so the SDT input must contain the R5-1 pair even though Q-Crate does not run an
R5-1 application in this milestone. Do not patch generated `pcw.dtsi` files or
enable an unrelated PL interrupt merely to make application generation pass.

### Vitis 2024.2 FreeRTOS IPI vector correction

The generated `amd_platform_info.h` assigns `IPI_IRQ_VECT_ID` the physical GIC
ID `0x41` (65). That value is not the representation consumed by this SDT-based
FreeRTOS BSP. Its interrupt wrapper extracts a relative interrupt number and
adds the 32-entry SPI offset. Passing 65 therefore installs and enables GIC ID
97, leaving the real R5-0 IPI at ID 65 pending but disabled.

The Vitis flow applies a guarded correction to the disposable generated header:

```c
#define IPI_IRQ_VECT_ID (XPAR_IPI1_INTERRUPTS & 0x0FFFU)
```

`XPAR_IPI1_INTERRUPTS` is `0x4021` for this platform, so the compact vector is
`0x21` (33). The FreeRTOS wrapper adds the SPI offset and programs GIC ID 65.
The compact value must be retained because libmetal also uses it as an index in
its interrupt-handler table; using the complete `0x4021` encoding would exceed
that table. The correction checks the exact generated definition and stops the
build if a future Vitis release changes it, forcing a review rather than a
silent rewrite of unfamiliar output.

The diagnostic signature on a failing image was:

- IPI observation/status at `0xff310010`/`0xff310014` showed an A53 request;
- GIC distributor `ISENABLER2` at `0xf9010108` had bit 1 clear;
- GIC distributor `ISPENDR2` at `0xf9010208` had bit 1 set.

Bit 1 in distributor bank 2 is GIC ID 65. Pending-but-disabled proves that the
mailbox request reached the RPU GIC and narrows the fault to R5 interrupt setup,
not Linux RPMsg transport, shared memory, or the IPI mailbox route.

PetaLinux appends the tracked `system-user.dtsi` to an already preprocessed
SDT with a devicetree `/include/`. A nested C `#include` in that file therefore
reaches `dtc` unexpanded. Its remoteproc power domains use the stable numeric
IDs from `xlnx-zynqmp-power.h`, with the binding names retained in comments;
do not reintroduce a nested `#include` without changing the recipe's complete
preprocessing model.

The Linux description follows the driver actually shipped in the PetaLinux
2024.2 `linux-xlnx` 6.6.40 kernel. That module matches the parent compatible
`xlnx,zynqmp-r5-remoteproc` and consumes child `xilinx,r5f` nodes with explicit
`sram` phandles. The same source tree also contains the newer upstream
`xlnx,zynqmp-r5fss` schema, but the shipped module does not advertise that
compatible. Selecting a device-tree schema without checking the built
module's `MODULE_DEVICE_TABLE` leaves the node present but permanently
unbound. Verify the installed contract with `modinfo zynqmp_r5_remoteproc`.
That driver also consumes the platform-firmware mode values directly:
`0` means lockstep and `1` means split. Q-Crate describes two R5 children and
therefore selects split mode with `xlnx,cluster-mode = <1>`; using the newer
schema's reversed interpretation makes the 2024.2 driver reject its probe with
`-EINVAL` before either remoteproc device is registered.

## Wire protocol

Every request and response is exactly 64 bytes and contains:

- magic and ABI version;
- command and transaction ID;
- payload length in 32-bit words;
- signed status;
- eleven 32-bit payload words.

| Command | Request | Successful response |
|---|---|---|
| `PING` | one nonce word | the same nonce |
| `GET_INFO` | empty | device ID, version, build ID, capabilities, stream clock, control clock |
| `SCRATCH_TEST` | one test value | original, requested, readback, restore target, restored readback |
| `GET_R5_STATS` | empty | tick count, tick rate, accepted requests, rejected requests |
| `SEQ_LOAD_BEGIN` | event count, payload CRC | accepted count and CRC |
| `SEQ_LOAD_EVENT` | index plus one four-word event | accepted index |
| `SEQ_LOAD_COMMIT` | empty | committed event count and CRC |
| `SEQ_GET_STATUS` | empty | PL status, counters, and 64-bit timing values |
| `SEQ_ARM` | external-trigger flag | current sequence status |
| `SEQ_START` | empty | current sequence status |
| `SEQ_ABORT` | empty | current sequence status |
| `SEQ_RESET` | empty | current sequence status |

Both processors are little-endian. Any future cross-endian target must add
explicit wire conversion without changing the existing ABI silently.

### Sequencer ownership transaction

The sequence protocol is deliberately transactional and fail-closed:

1. Linux validates the complete `.qseq` file before contacting R5.
2. `SEQ_LOAD_BEGIN` records the expected event count and payload CRC only when
   the PL is idle, unlocked, and fault-free. It invalidates any older commit.
3. Ordered `SEQ_LOAD_EVENT` requests repeat the format and safety checks in R5,
   write four APB words, read them back, and extend an incremental CRC.
4. `SEQ_LOAD_COMMIT` succeeds only after all events arrive and the CRC matches;
   R5 then writes and reads back the PL event count.
5. ARM and START are rejected until a sequence is committed. ABORT and RESET
   use bounded state waits, so a failed PL transition cannot block R5 forever.

R5 returns the eleven-word hardware status snapshot for status and lifecycle
commands. Status bit 30 means an upload is active and bit 31 means R5 has a
committed sequence. These two bits describe R5 ownership state and are not PL
register bits. Upload errors invalidate the transaction; Linux must start again
with `SEQ_LOAD_BEGIN`. The fixed message remains 64 bytes, but the wire ABI is
version 2 because the command and status contract changed.

### Worked extension: R5 service statistics

The `qcrate-control stats` extension is the reference example for adding a
bounded control feature across the existing OpenAMP transport:

1. `common/protocol/qcrate_protocol.h` assigns command ID 4 while preserving
   the fixed 64-byte ABI.
2. `qcrate_rpmsg_service.c` validates the empty request, reads the FreeRTOS tick
   counter and configured tick rate, and returns service counters.
3. `qcrate_control.c` creates the request, validates the four-word response,
   and formats uptime using integer arithmetic.
4. `vitis_flow.py all` copies the tracked protocol and R5 service into the
   generated application, builds the ELF, and stages the ELF and Linux inputs
   for the Yocto recipe.

An accepted request is any callback that produces `QCRATE_STATUS_OK`; all
other callbacks are rejected. The statistics request includes itself. The
counters describe requests processed by R5, regardless of whether sending the
response later succeeds, wrap modulo 2^32, and reset when Linux remoteproc
reloads the R5 firmware. The FreeRTOS tick count also wraps according to
`TickType_t`; this diagnostic reports current firmware uptime, not wall-clock
time.

The statistics extension required no XSA, device-tree, kernel, carveout,
endpoint-name, or Yocto recipe change. The sequencer ownership extension has
the same boundary: it changes the shared protocol, the R5 endpoint, and Linux
userspace, while reusing the established transport and lifecycle layers.

## Reserved-memory contract

The Linux device tree starts from AMD Vitis 2024.2
`openamp-overlay-zynqmp.yaml`, with one required correction described below:

| Owner | Purpose | Address | Size |
|---|---|---:|---:|
| R5-0 | firmware carveout | `0x3ed00000` | `0x60000` |
| R5-0 | vring 0 | `0x3ed60000` | `0x4000` |
| R5-0 | vring 1 | `0x3ed64000` | `0x4000` |
| R5-0 | RPMsg buffers | `0x3ed68000` | `0x40000` |
| R5-1 | corresponding reserved range | `0x3ef00000` onward | same layout |

The vendor YAML declares R5-0 vring 0 as only `0x2000` bytes. With the
resource table's 256 descriptors and `0x1000` alignment, Linux 6.6 calculates
`PAGE_ALIGN(vring_size(256, 0x1000))` as `0x3000`. The undersized carveout
therefore makes `rproc-virtio` fail with `Registered carveout doesn't fit len
request` and `-ENOMEM`. Q-Crate reserves the complete non-overlapping
`0x3ed60000` through `0x3ed63fff` window (`0x4000` bytes). This also makes the
R5-0 layout consistent with the vendor template's other vring carveouts.

Linux 6.6's current `xlnx,zynqmp-r5fss` driver requires two available R5 child
nodes in split mode, so the device tree describes both cores. The Q-Crate
service starts only R5-0; R5-1 remains stopped and reserved for later work.

These addresses are a cross-tool contract. If the Vitis OpenAMP overlay changes,
update and review the Linux reserved-memory nodes before booting the firmware.

## Build and stage

The accepted XSA must already exist at `build/artifacts/qcrate_kv260.xsa`.
There is no Vivado rebuild for this software-only milestone.

From the repository root, build the generated R5 platform/application and
stage the ELF plus shared source inputs for BitBake:

```bash
python3 kv260/vitis/vitis_flow.py all
```

Expected final staged files are:

```text
build/artifacts/qcrate-r5.elf
kv260/linux/petalinux/qcrate-kv260/project-spec/meta-user/
  recipes-apps/qcrate-openamp/files/qcrate-r5.elf
  recipes-apps/qcrate-openamp/files/qcrate_control.c
  recipes-apps/qcrate-openamp/files/qcrate_protocol.h
  recipes-apps/qcrate-openamp/files/qcrate_rpmsg_client.c
  recipes-apps/qcrate-openamp/files/qcrate_rpmsg_client.h
```

`build` and `stage` can also be run separately:

```bash
python3 kv260/vitis/vitis_flow.py build
python3 kv260/vitis/vitis_flow.py stage
```

The `build` action recreates only `build/vitis/workspace`; it does not touch
tracked source or the Vivado project.

## PetaLinux build and deployment

First compile the new recipe alone. This gives a short, causal error if the
client, firmware staging, or systemd package is wrong:

```bash
source /tools/Xilinx/PetaLinux/2024.2/settings.sh
cd kv260/linux/petalinux/qcrate-kv260
petalinux-build -c qcrate-openamp
cd ../../../..
```

Then rebuild and deploy the full image, replacing the whole-card path after
checking it with `lsblk`:

```bash
lsblk -o NAME,PATH,SIZE,MODEL,SERIAL,TRAN,FSTYPE,LABEL,MOUNTPOINTS
python3 kv260/linux/petalinux/scripts/petalinux_flow.py all \
  --device /dev/mmcblk0
```

This updates the kernel modules, base device tree, root filesystem, R5 ELF, and
client on the SD card. It does **not** require `xmutil bootfw_update`: this
milestone does not change the accepted FSBL/PMU/TF-A/QSPI clock-init contract.

## Board acceptance

Boot the deployed card. The service starts automatically after
`qcrate-pl-load.service` and should bind the announced channel to
`rpmsg_chrdev`.

```bash
sudo systemctl status qcrate-pl-load.service qcrate-r5.service --no-pager -l
sudo journalctl -b -u qcrate-r5.service --no-pager -l

for node in /sys/class/remoteproc/remoteproc*; do
  printf '%s: ' "$node"
  cat "$node/name" "$node/state"
done

for node in /sys/class/rpmsg/rpmsg*; do
  printf '%s: ' "$node"
  cat "$node/name" "$node/src" "$node/dst"
done

sudo qcrate-control ping 0x12345678
sudo qcrate-control info
sudo qcrate-control scratch-test 0xa5a55a5a
sudo qcrate-control stats
sudo qcrate-control test
sudo qcrate-sequence status
```

Expected acceptance evidence includes:

```text
qcrate-r5.service: active (exited)
qcrate-control
PASS ping 0x12345678
DEVICE_ID       : 0x51435254
stream clock    : 200000000 Hz
control clock   : 100000000 Hz
R5 uptime ticks : 123456
tick rate       : 1000 Hz
accepted        : 4
rejected        : 0
PASS Q-Crate OpenAMP vertical slice
```

Also confirm the existing Linux-owned DMA path still works after R5 starts:

```bash
sudo qcrate-dma capture
```

Compile and copy a sequence from the development PC, then exercise the
R5-owned control path:

```bash
python3 host/sequence_compiler/qcrate_sequence.py compile \
  host/sequence_compiler/examples/two_channel_demo.json \
  /tmp/two_channel_demo.qseq
scp /tmp/two_channel_demo.qseq \
  petalinux@<kv260-ip>:~/qcrate/two_channel_demo.qseq

sudo qcrate-sequence test ~/qcrate/two_channel_demo.qseq
sudo qcrate-sequence status
```

Expected evidence includes `PASS R5 loaded and committed 4 events`,
`PASS R5 armed 4 events`, `PASS R5 shot 1`, and a final idle status with one
completed shot. `qcrate-apb` still permits sequence-page reads for diagnosis,
but refuses writes unless the explicit unsafe owner-override option is given.

The board acceptance completed successfully with the fixed 200/100 MHz PL
clocks, the R5-0 remote processor running, and the `qcrate-control` RPMsg
channel responsive. The R5-owned sequencer upload, CRC/readback, ARM, START,
completion, and status path passed, and the existing Linux-owned DMA capture
continued to pass.

## Failure diagnostics

If `qcrate-r5.service` fails, collect only the first causal evidence:

```bash
sudo journalctl -b -u qcrate-r5.service --no-pager -l
sudo dmesg | grep -Ei 'remoteproc|r5f|rpmsg|virtio|ipi' | tail -100
sudo sh -c 'mountpoint -q /sys/kernel/debug || mount -t debugfs none /sys/kernel/debug'
sudo cat /sys/kernel/debug/remoteproc/remoteproc0/trace0
find /sys/class/remoteproc -maxdepth 2 -type f \
  \( -name name -o -name state -o -name firmware \) -print -exec cat {} \;
find /sys/bus/rpmsg/devices -maxdepth 2 -type f \
  \( -name name -o -name src -o -name dst -o -name driver_override \) \
  -print -exec cat {} \;
```

Do not change carveout addresses or load R5-0 manually through XSDB while
Linux remoteproc owns it. Stop the systemd service first when lifecycle testing
is required:

```bash
sudo systemctl stop qcrate-r5.service
sudo systemctl start qcrate-r5.service
```
